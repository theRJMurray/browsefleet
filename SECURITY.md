# Security Policy

## Supported versions

BrowseFleet is in active development. We support the latest minor release on the `master` branch. Security fixes for older releases are best-effort.

| Version          | Supported |
| ---------------- | --------- |
| `0.x.x` (latest) | yes       |
| older            | no        |

## Reporting a vulnerability

Please do **not** open a public GitHub Issue for security findings. Email the maintainers at:

> `therjmurray+browsefleet-sec@gmail.com`

Include:

- A clear description of the vulnerability and its impact.
- Reproduction steps or a proof-of-concept.
- Affected version, commit SHA, or Docker image tag.
- Whether you have already disclosed this to anyone else.

If you would like to encrypt your report, request our PGP key in your initial email and we will reply with the public key on a separate channel.

## What to expect

| Stage                                      | Target response                                                                                 |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Acknowledgement                            | within one business day                                                                         |
| Initial triage and severity classification | within five business days                                                                       |
| Mitigation plan or fix availability        | depends on severity; tracked publicly only after a fix is shipped                               |
| Public disclosure                          | coordinated with you; default 90 days from report or at release of the fix, whichever is sooner |

## Out of scope

The following are not treated as BrowseFleet vulnerabilities:

- Bugs in third-party dependencies that have not been demonstrated to affect BrowseFleet's behavior. File those upstream (`puppeteer-core`, `hono`, `better-sqlite3`, etc.).
- Self-inflicted misconfigurations (running with `API_KEYS=` unset on a public network, exposing the CDP proxy port without authentication, etc.). A deployment hardening guide lands as part of the Phase 2 docs build-out; until then, the safe defaults are: set `API_KEYS` to a long random list, terminate TLS in front of the server, and do not expose port 3000 directly.
- Issues in test fixtures, example code, or documentation.
- Reports generated by automated scanners without manual validation.
